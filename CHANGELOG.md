# Changelog

## [Unreleased]

### Security

- known risk: a document typed from the names of its first entries (docx, xlsx, pptx, odt, epub, jar, apk) that the check cannot hold to its budget is no longer tested member by member: this happens when it has more than `recursive_extract_max_files` entries or `recursive_extract_max_size` bytes, or when it is a member of an archive that has used up most of that budget. It is then analyzed whole by GMalware and delivered with its members listed as `extract-limit`, but only if its technical listing marks every member as plain. A member marked encrypted follows `unanalyzable_policy.encrypted`, and a listing that cannot be read follows `extract_error`. Remaining risk: a ZipCrypto member whose encryption flag is cleared in both its central and its local header is not seen. A flag cleared in only one of the two headers is caught, and so is an AES member, which 7-Zip names by its method. The same goes for data hidden before or after the document. In both cases the document is delivered with that content unchecked. Catching such a member would mean testing the data of every member, which the check does not do over the limits. Inside an archive this needs no padding: filling the parent archive to the limit is enough.
- dependencies: echo 4.16.1, golang.org/x/crypto 0.59.0, x/net 0.62.0, x/text 0.44.0, x/sys 0.50.0, brotli 1.2.7, klauspost/compress 1.20.2. Three advisories have no upstream fix and are not reachable: GO-2026-6875 and GO-2026-6872 (echo proxy and rate limiter middlewares, unused) and GO-2026-5932 (golang.org/x/crypto/openpgp, pulled by the archive library at init only, never called)

### Added

- `unanalyzable_policy.analysis_error` (`error` by default, `mitigate` or `pass`): what becomes of a file the analysis failed on and found no detection in. `error` keeps today's behavior (the file stays in INPUT as an error), `mitigate` makes it malware with the reason `analysis-error` (what the `error_filter` plugin gave), `pass` delivers it marked `not-analyzed-reason: analysis-error` (new reason, in the JSON reports, the PDF and the console line, "content not verified"). A file with a detection is malware whatever this value. `pass` delivers files that a depositor can usually make fail: see the README
- session: the reports of an open session are kept on disk (`<work_dir>/session/<random>.jsonl`, JSON Lines, mode `0600`) and no longer in memory: the RAM of a session no longer grows with its size, only the reports in error stay in memory (16 MiB for the plugin, then spilled to the spool with a warning; a later success of the same file then adds a second line). New keys `max_duration` (default `24h`, must be positive) and `max_spool_size` (default `1GiB`, at least `1MiB`) close a session at once; the next deposit opens a new one. A spool that cannot be written (disk full) closes its session at once, reported with what it holds, with the console error `session-spool-error`; if even the JSON report fails, the spool is copied as is (`.jsonl`). The spools of a crashed run are deleted at the next start with a warning that gives the number of session reports lost (no recovery). The session plugin refuses a connector that has no work directory. In a session report the reports in error held in memory now come last, sorted by file name, after the others in arrival order. New `datamodel.SessionSpoolDir` (the folder of the spools under the work directory) and `datamodel.SessionSpoolExt`
- monitoring: a `modification_delay` under 1 s is accepted, and logs a warning each time the configuration is applied (at start, and at a reconfiguration by the console) that says what it risks: a file still being written may be analyzed incomplete, and a rewrite of the same size within one timestamp tick of the file system is not seen by the identity check (the delay must exceed the timestamp granularity of the file system)
- report plugin: the PDF has a section "Fichiers non analysés" and a counter for the files and archive members that reached the output without a complete analysis (reason in plain words, archive of origin), so that what `unanalyzable_policy` lets through and what a filter plugin waives is visible in the session report
- report plugin: the PDF is bounded. Every section stops at 300 rows with "… et N autres", the counters stay exact, the count of the failed members of an archive included, however many failed (up to 2^30); the blocked archives and their malicious members share the 300 rows of their section (3 rows per archive plus one per member). Every name, error and threat shown in the PDF is cut to 100 bytes (control, invisible and bidirectional characters become "�", ZWNJ and ZWJ included, so some Persian or Indic names and emoji sequences show "�" in the PDF; a file shows at most 2 threat names then "… (+N autres)"; the JSON report keeps more: up to 64 threat names per file, each text up to 1024 bytes, within its 4 MiB bound), so that long names cannot lengthen the rendering; the worst cases are measured with the real browser by a test, which checks the size always and the time on demand (`HC_WORST_CASE_TIME=1`), under half of the 5 minutes and 64 MiB the rendering is bounded by on a machine that is not overloaded. Custom templates must be updated to show the new data (`NbFileNotAnalyzed`, `NotAnalyzedFiles`, `More*`, `MoreExtracted`)
- report plugin: under extreme load (a load average of about 19) rendering the worst-case PDF can exceed the 5 minutes of the rendering timeout; the attempt then fails like any other failed generation (1 + `report_retries` attempts, one per check, about 24 minutes with the defaults for a session alone, and more when other sessions wait, since their attempts follow one another) and the session gets its JSON report instead; the real-browser test of the worst cases can fail on an overloaded machine (it checks the size always, and the time only with `HC_WORST_CASE_TIME=1`, as do the extract zip-walk tests on a million entries)
- report plugin: a report with an error is listed among the files in error and no longer counted as analyzed (a file whose action failed, such as a quarantine, is in error and not analyzed); the failed members of an archive are counted once, not again with the summary error of their archive
- datamodel: new `ExtractedErrorsTransient`, `ExtractedErrorsPermanent`, `ExtractedErrorsSummary` and `IsExtractedErrorsSummary`: the one place where the summary error of an archive with failed members is built and recognized, by the scanner and by the report plugin
- datamodel: new `UniqueKey`, `CutText`, `MoreErrorsKey`, `MoreErrorsText`, `ParseMoreErrors`, `ListedErrors`, `MaxFileCount` and `AddCount`: the one place where the keys of the failed files of an archive are made (unique, valid UTF-8, within 1 KiB, the key of the count of the files not listed kept apart) and where a text is cut, used by the scanner, by `Report.Bound` and by the report plugin; `Bound` keeps the count of the files not analyzed to `MaxFileCount` and the plugin adds its counts without wrapping around, so that an absurd count set by a plugin cannot make a count negative. `Bound` also adds the entries it leaves out to the count of the files not listed, so that the entries listed and that count always make the number of failed files
- stop on a signal: `SIGTERM` and `SIGINT` stop the connector like the order of the console (`agent`, `monitoring` and `scan`; before, the process died on `SIGTERM` without closing anything, leaving its work directory, an extraction in progress, and the reports of the open sessions). New local key `shutdown_timeout` (flag `--shutdown-timeout`, default `8s`, at least `2s`): files being processed finish within it minus a reserve, are then cut and left in place, the sessions write their report, the plugins close (the `extract` plugin kills its 7-Zip) and the work directory is removed; a second signal stops at once; a summary is logged; exit code `1` if the delay was exceeded. `Connector.Shutdown(drain, closing)`, `Handler.Shutdown` and `plugins.Interrupter` are new. Fix: after a stop whose wait was cut, the plugins used to be closed with an expired context and could no longer write their reports; they now always get a live one
- quarantine: `quarantine.format: zip` writes password-protected ZIP files (ZipCrypto) openable with common archive tools; `tar` stays the default and both formats are always restorable. With `zip`, the quarantine password must be considered public (warning at each configuration)
- monitoring: `monitoring.disable_fs_watcher` (flag `--disable-fs-watcher`) stops all filesystem watches, files are found by the pre-scan and the periodic rescan only; it requires `monitoring.period` (configuration refused otherwise). Settable from the console

### Changed

- file names: one set of hidden characters (the Unicode default-ignorable characters, such as bidirectional and zero-width characters, soft hyphen, variation selectors and blank fillers, plus controls, U+2028, U+2029 and U+2800) is now shared by the PDF, the GMalware label, the console line, the quarantine entry name, the 7-Zip output, `quarantine list` and the final error of the CLI. An emoji variation selector (U+FE0F) shows as "�" like ZWJ. The label sent to GMalware replaces them by `_` (the full host path is still sent), and the console `inform` line shows them as "�" for the file, the quarantine location, the destination and the threat names. The console `inform` line now quotes `file` and `details` (`file: "/in/a.zip"`, `details: ["Evil" "/q/x.lock"]`): a name can no longer forge a field or a line, and anything that parses this line must read the quoted form. The JSON reports and the logs keep the raw name on purpose: they are records for machines, and a lossy mapping would make two names identical. Path rules get a third, folded form of the name, without its hidden characters and its invalid UTF-8 bytes: a `forbidden_paths` rule matches if any form matches (`\.exe$` now catches `a.exe` followed by a zero-width space or a newline), a `skipped_paths` rule must match all of them. Known limit: spaces that pad a name and look-alike letters are not covered
- a zip-family document (docx, xlsx, jar, apk…) over the check limits (`recursive_extract_max_files`, `recursive_extract_max_size`, or the budget left by the archive it is a member of) is analyzed whole and delivered when nothing is found, instead of being held in INPUT in error: no `unanalyzable_policy` applies to its members, which are listed among the files not analyzed with the reason `extract-limit` (the document counts as analyzed), only when the document is delivered. A detection or an analysis error still decide. Ordinary archives over the limits are unchanged. `ExtractLimits.CheckOnly`: an extractor now gives back every member of a listing over the budget as skipped, not only those beyond it
- agent: at a stop, the connector waits for the console loop, within the delay of the stop, so that the tasks it had fetched and will not run are acknowledged with an error ("connector stopped before running the task") at once, instead of leaving them to the console's 15-minute timeout. A task still running when the delay of the stop ends, or one whose acknowledgement does not get through in time (a console that does not answer), keeps that timeout; a task that finishes is acknowledged with its real result. Needs the SDK that acknowledges them
- a restored file that is delivered is listed as not analyzed with the reason `restored` (JSON reports, PDF, and the `inform` console line, which now prints it even without `--verbose`, as `not analyzed (restored)` instead of `seems safe`); it was already counted as restored. A refused restored file, or one a plugin found malicious, has no such reason
- GLIMPS Malware Detect submissions (behavior change): a member of an archive is submitted under the path of its archive followed by its own path (`/in/a.zip/d/evil.exe`), where it used to carry a path in the work directory; a plain file keeps its host path. The name is capped at 4096 bytes, keeping its end preceded by `…`
- report plugin: the rendering timeout of the PDF goes from 2 to 5 minutes, and the default `report_timeout` of the `session` plugin from 2 to 6 minutes (it covers the rendering, the wait for one of the 2 browsers and the writing of the PDF to every export, so it must exceed the rendering timeout; raising the rendering timeout alone would change nothing). A plugins file that sets `report_timeout` (the README example had `2m`) keeps it: raise it to `6m` or remove it. A heavy session can now hold a browser for up to 5 minutes, and delay the reports of the other sessions by up to 6 minutes per attempt; the JSON report of a session alone comes after about 24 minutes instead of about 8 when every attempt fails. A failed attempt is still retried (`report_retries`), then a JSON report is written
- feat!: the `filepath_filter` and `error_filter` plugins are removed, from the sources, the packages (`.goreleaser.yml`), the example plugins file and the README. Their entries in the plugins file (by their name, or by `filepath_filter.so`, `filepath.so`, `error_filter.so`, and the binaries `filepath_filter` and `error_filter` of the packages; a plugin of anyone whose file has one of these base names is dropped too) are ignored and never carried over (an entry is never refused on its own; a plugins file with nothing else is), with a warning in the log and a console error for as long as they are there (`plugin-removed-filepath-filter` and `plugin-removed-error-filter`, resolved once they are gone); a plugins file that holds only removed plugins is refused. **On upgrade a deny-list left in the plugins file stops applying until it is set in the main configuration** (when the dropped entry had `forbidden_paths` and the main configuration has none, the warning and the console error say outright that the deny-list is NOT enforced; it stays a warning, not a refusal) (`filepath_filter.forbidden_paths`, `filepath_filter.skipped_paths`), and the files whose analysis fails stay in INPUT (`unanalyzable_policy.analysis_error: error`) until `mitigate` is set to quarantine them as the plugin did. Known risk, unchanged: a skip pattern that is not anchored on a folder that depositors cannot create lets them name a file or a member so that it is not analyzed
- restored content (behavior change): a content restored from quarantine waives the analysis only, never a refusal. Before, a restored content deposited anywhere skipped the plugins and the path rules; now the path rules of the configuration and the `OnScanFile` chain run for it first, and a refusal wins (a content under a forbidden path, or of a forbidden type, is refused as any file is: quarantined although its content was restored, through `quarantine.WithRefusedAnyway`, which only the scanner sets, with the restored mark of the content kept, so that the same content elsewhere stays allowed; without the quarantine action it is deleted if that is configured, else left in INPUT, reported, with a final outcome and no retry), while a waiver (a skipped path, a plugin that lets it through) changes nothing and the content is delivered as restored, without analysis. A restored archive is also listed (never extracted nor analyzed) when `forbidden_paths` is set: a member at a forbidden path refuses and quarantines it, the member named in `MaliciousSubfiles`; members that cannot be known make an error refusal (final, not analyzed again), and an extractor that is down a retry. With `delete` on and the quarantine off, a refused restored file is deleted. The members of an archive are unchanged: they are analyzed as before.
- analysis errors (behavior change): an archive with a member the analysis failed on is now an error in the reports ("N extracted file(s) could not be analyzed") and no longer counted as analyzed; a file unanalyzable by nature (encrypted, left unopened by the limits) follows its own policy first, so with `encrypted: error` it stays in INPUT as an error whatever `analysis_error` says (the `error_filter` plugin is removed: nothing makes it malware but `analysis_error: mitigate`), and `analysis_error: pass` marks the file it delivers `analysis-error`, never `encrypted` or `extract-error`
- analysis: the name submitted with a file has its control characters (C0, DEL, C1) and the line and paragraph separators replaced by `_`, and invalid UTF-8 by U+FFFD. A file whose name held one was refused by the service ("error submitting file"), never delivered, and retried until the connector gave up.
- extract plugin: a folder entry deflated on its own (no size, the 2 bytes of an empty Deflate block) in a zip is no longer taken for a folder that holds data (it kept such an archive in INPUT); any other packed size is an anomaly. The plugin now walks the headers of every zip itself (extraction and check-only, so also the documents and packages that are delivered whole; no decompression beyond 16 bytes of a folder, no name, no password, at most 10 s) and refuses what 7-Zip does not see and unzip or a streaming reader does: a local record that the directory does not list (between the entries, after the last one, before the first), entries at the same place, a folder that holds data in its local header (named with a slash or a backslash, marked by an attribute, in a method other than Stored or Deflate), several ends of directory, a data descriptor that is not the one of the directory. An APK Signing Block between the last entry and the directory is allowed, parsed exactly and at most 1 MiB (honest blocks measured 1.4 to 18 KB; the bound was 16 MiB in the earlier versions of this work, so a block over 1 MiB is a new refusal). The entries of the directory must fill it exactly, and the number of entries 7-Zip lists must be that of the directory plus, when a record the directory does not list comes before the first entry, one for each such record (the zero records and the stamp alike); any other count is an anomaly. Zips with unused space that is not made of zeros between their entries are now refused: that is the known limit of the previous versions (a gap) closed, and it stays an extract-error under the default policy; zero padding (APK signing tools, aligners) is accepted. A deflate stream that ends before its data, which 7-Zip reports as data after the end of the payload, is an anomaly and no longer a failure that is retried for ever. Two kinds of unlisted local record that honest APKs carry are accepted (a record of nothing, anywhere, and one Google Play source stamp), the names of the local and central headers are compared with the ASCII letters folded, and the method and encryption bit of every local header must be the directory's. Tar, 7z and the other formats keep the listing rule only. A folder with no name, or a name that is too long for a file system, is an anomaly. The type of the archive is read from its first `Type =` line even when that line has no name (a comment could add a second one)
- extract plugin: the zip bomb rule weighs what the listing gives: the members within `max_file_size` declare more than 3 GB and either pack, with every member counted (the ones over the limit too, since a solid 7z lists its block on its first member), to less than a hundredth of it, or to no byte at all. Before, the ratio of a size over nothing was not computed, and a forged archive that packed to nothing was taken for one the budget leaves out; a solid 7z of zeros whose first member is over the limit, or one member over the limit that packs to a byte, no longer hides gigabytes. What the members pack to is capped at the size of the archive file, so that a forged entry that declares tens of gigabytes of packed bytes cannot dilute the ratio of the others (an archive file whose size cannot be read is a failure of the host, retried: never a clamp that is skipped). A blank packed size (Cab, Compound: MSI, .doc, .xls) is not a size of 0, and an archive whose listing gives none (bzip2, and Cab or Compound when they give none) is no bomb; file systems and disk images are exempt from the ratio altogether (an empty 10 GiB QCOW2 is 196 KB). A size of 13 digits or more, which does not fit its column in the listing, makes the archive an anomaly (a member of 1 TB or more). A sparse tar made only of holes is taken for a bomb. A listing with no packed size never divides by zero (it crashed the connector in a first version). A document checked when the budget of the extraction is exactly spent is passed to the extractor
- path rules (behavior change): the connector applies `filepath_filter.forbidden_paths` and `skipped_paths` itself (the main configuration, before the plugins; a forbidden path beats a skipped one, a refusal of a plugin beats both), and the `analysis_error` and `filepath_filter` keys are no longer refused as not implemented. Both lists are bounded, in the validation of the console and in the connector (256 patterns per list, 1024 bytes each, 32 KiB in all, counted repeats of 100, an estimated size of 512 instructions per pattern and 4096 in all and 4096 rune ranges, from the parse tree, so that nothing is compiled before it passed; paths of 4096 bytes: a longer one is never skipped and, with `forbidden_paths` set, fails as an error). The logical path and the path as the file system gives it are both matched (forbidden if either matches, skipped if both do), and the top-level archive is matched like any file. A skipped archive is listed, not extracted: the new `ExtractLimits.NamesOnly` mode asks the extractor for the names of the members (`Extraction.Names`; the extract plugin gives the technical listing and the walk of the zip headers, no test, no decompression, no size budget; the default extractor returns `ErrListingUnsupported`), so that a forbidden member still refuses the archive and is named in the report. When the names cannot be known (no extract plugin, a listing error, headers that need a password, more members than the budget, anything wrong with the archive) the skip is withdrawn and the archive is analyzed like any other. Under `encrypted: pass` or `extract_error: as_file`, such an archive is delivered whole without `forbidden_paths` having seen its members. The listing counts against `recursive_extract_max_files`, and the matching of the names of the archives of one file is bounded to 30 s (an error that leaves the file in INPUT). While the `filepath_filter` plugin exists both apply; a refusal of the core returns first
- extract plugin: the check run at every start also exercises the technical listing (`-slt`) that the encryption decision relies on, on the reference archive (it must report the data after its end and list its 3 members), and a member whose path has a component over 255 bytes is an anomaly (the archive is damaged, no endless retry), as is a member the file system refuses at extraction (a name too long after a rename on a clash, a path over `PATH_MAX`), and so is an entry flagged as a folder that holds data (7-Zip never extracts it, other readers do). Behavior change: a member left out as an anomaly (name, component or depth) was never extracted nor tested, so the archive is no longer proven free of encryption by the flags of the other members: under `extract_error: as_file` such an archive is no longer delivered, the policy of the encrypted files decides. README: known limitations of the encryption check
- archives (a detection always wins, in archives too): the `OnScanFile` plugins decide on a sub-archive where they decide on a top-level one, once for each of them (an empty sub-archive included), after its extraction and before any of its members is sent, so a waiver or a refusal can no longer replace what the members and their siblings found (before, the first worker to take a member of a sub-archive made the call, and a waiver given after a detection could deliver an archive that holds malware). A result given to a whole archive is merged into what its members found, never replaces it, and is refused while members are in flight. An extractor that goes down while members of an archive are still being analyzed no longer ends the file at once: the archive waits for them, and ends with a detection among them (quarantined or deleted, the members never sent listed as errors) or, with none, is left in place and retried as before; the descriptor of the file stays open until then. A result that is malware always has a reason (`malware-detected` when a plugin or a merge leaves it empty), in the reports, the console lines and the mitigation events. The plugins are given the descriptor path of a top-level archive, as for any other file, instead of the path it was deposited at (the logical name keeps its control characters neutralized as before; a sub-archive lives in the work directory and has no other path), so a path swapped after the core opened the file cannot make a plugin type or stat another file
- plugins (breaking change): the `filesize_filter` plugin is removed, from the sources, the packages (`.goreleaser.yml`), the example plugins file and the README. An entry for it in the plugins file (by its name, or naming `filesize_filter.so` or `filesize.so`) is not loaded and does not fail the start (unless the plugins file has nothing else, which is refused): it logs a warning that names each ignored entry and the policy of `too_big` in force, and raises the console error `plugin-removed-filesize-filter` at each configuration applied (resolved by the next one without the entry). Oversized files are no longer quarantined by a plugin: set `unanalyzable_policy.too_big: mitigate` to keep that behaviour (nothing is switched on for you: the policy stays `error`, an oversized file stays in INPUT as an error). The warning is also reported again when a rollback replays a configuration that has such an entry, and its text is bounded (50 entries, 256 bytes each)
- plugins: the contract of `GenerateReport` is stronger: after `Content.Close` returns, the generator no longer reads the sequence of reports, and it stops when its context ends even if nobody reads the content. The connector enforces it (the sequence ends and yields nothing once the content is closed), the default generator now waits for its writer in `Close`, and the `report` plugin stops reading at the end of the context. Third-party generators must honour it
- actions (behavior change): when quarantining, moving or removing a file fails, its report now carries a short error ("the file could not be quarantined", "…moved to the destination", "…removed"; the cause stays in the log, and no path is added), where it used to carry none. The file is therefore counted as in error, not as analyzed, in the session reports and the PDF, and, while the connector runs, a failure repeated on a file that is still in INPUT (to be retried) opens no new session; a file that left INPUT after an error (quarantined, deleted or moved) is not remembered, so that the same bytes dropped again get their session. The lock report written next to a detection that could not be moved carries the same text. A quarantine refused because the content was restored is not a failure (the next pass handles the file as restored). A file whose analysis failed (without an error of the pipeline) gets "the file could not be analyzed" (the text of the service stays in the log), so that it is counted as in error and not as analyzed; an archive that lists its failed members is not an error of its own. A restored file whose action failed now has its report sent too. An error the report already had (of the analysis, or a refusal with its own reason) is kept
- session: the empty folders left below a session are removed once its report is written (`remove_empty_dirs`, **on by default**, `cleanup_timeout` 2m; Linux only; `false` restores the previous behavior). Announce it: a tree of empty folders a user prepared before depositing is removed after `delay` of inactivity. The root folder, the session folders and the folders changed less than `delay` ago stay; nothing is followed (every folder is opened from its parent with `O_NOFOLLOW` and removed with `unlinkat(AT_REMOVEDIR)`), at most 128 levels are walked. The removal runs in its own goroutine after the report (never at stop, never delaying a report), keeps the work directory by device and inode, and logs what it removed, kept and failed to remove
- unanalyzable files (behavior change: with the default `too_big: error`, an archive with a member over `max_file_size` now stays in INPUT as an error, for good and without a second extraction, where it used to be moved as clean; and an archive a plugin lets through, by `skipped_types` or a path rule, now reaches the output marked `policy-skipped`, where it used to stay in place because its hash was lost): `unanalyzable_policy.too_big` and `unanalyzable_policy.encrypted` (`error` by default, `pass` or `mitigate`) and `unanalyzable_policy.empty` (`skip` by default, or `mitigate`) are supported; `empty` defaults to `pass`, which is a behavior change: an empty file left in INPUT used to be skipped, and is now delivered as a new empty file (marked `empty` in the reports) and its source removed. Set `unanalyzable_policy.empty: skip` to keep the previous behavior. The `scan` command now analyzes empty files too (the default policy) and prints `not analyzed (empty)` for them without `--verbose`; use `unanalyzable_policy.empty: skip` to ignore them as before. `pass` needs `move.mode: copy` while the move action is on, and the console refuses to save that combination: it is refused with `rename`, and when the key is left out with `rename` the effective policy is `skip`, with a warning at each start, so that a site kept in `rename` still starts. Behavior change: an archive whose password is unknown (or whose encryption 7-Zip cannot name) was submitted as a plain file and moved as clean; with the default `encrypted: error` it now stays in INPUT as an error, visible in the log and the reports. An archive is now extracted, or listed to find out it is encrypted, whatever `extract_min_size` (a password-protected zip of a few KB used to be submitted as a plain file and moved), and an archive that the depth or the budget of the extraction does not let open (`recursive_extract_max_depth`, `recursive_extract_max_files`, `recursive_extract_max_size`) used to be analyzed as a plain file and now follows `too_big` as well, listed as `extract-limit`; an archive that fails for good under `error` is reported with its error. Members the extraction leaves out because of its limits follow `too_big` too: by default the archive stays in INPUT as an error (it used to be moved with them unanalyzed), with `pass` they are listed as not analyzed, with `mitigate` the archive is malware (`too-big`). `pass` marks the file `not-analyzed-reason` (`too-big`, `encrypted`, `empty`, or `policy-skipped` for a file an `OnScanFile` plugin let through, now visible in every report), with the new `Result` and `Report` fields `NotAnalyzedReason`, `NotAnalyzedSubfiles` and `NotAnalyzedExtractedFiles` (capped at 1000, exact counts); `mitigate` gives the result the former `filesize_filter` gave (`too-big`, `empty`, `encrypted` malware reasons, mapped to the console reason `invalid`). A file too big let through by `pass` is moved by name, as in `rename` mode, and says "content not verified". A `Report` is bounded by construction (`datamodel.MaxReportSize`, 4 MiB). `Report.Error` carries the error of the file. An `OnFileScanned` plugin cannot erase `NotAnalyzed*`. The core now sets `Source.TooBig` itself, from its own decision
- unanalyzable files: `unanalyzable_policy.extract_error: as_file` is supported (default `error`). An archive that the extractor finds damaged or inconsistent is, with `as_file`, analyzed as a plain file and delivered when nothing is detected, marked `extract-error`, **only when 7-Zip proved that it holds no encrypted content** (complete listing, no failure on the data of any member, every member plain and extracted, no data before or after the archive, which can hold another archive that 7-Zip does not list): warnings of the headers, members that share a name and names with a control character only. A member left out as an anomaly (a name or a path component too long, a path too deep, an entry flagged as a folder that holds data) is never extracted nor tested, so such an archive follows the encrypted policy. Any other damaged archive follows `unanalyzable_policy.encrypted`, and the report error says "encrypted, or damaged and it cannot be told which". A warning and the console error `extract-error-as-file` are raised at each configuration applied with `as_file`. Behavior change with the default `error`: a damaged archive is now a definitive failure (one report with a fixed error text, stays in INPUT, no retry) where it was retried silently without a report; a 7-Zip killed, cut by its timeout, a failure of the host or an extractor that is down is still retried, and an output flood of 7-Zip, which used to be retried, is definitive. The type is read once, before the extractor works, and a type that cannot be read counts as an archive. Costs one more read and write per moved file; a copy slower than `min_throughput` (plus a minute) or finding the destination full is abandoned and retried as a failure of a resource, with the console event `host-move-resource`. The empty content is matched per location only. The registry is searched through an index created at opening (existing registries are migrated). `Quarantiner.IsRestored(ctx, location, sha256)` takes the location; `Quarantine` of an entry already restored returns `quarantine.ErrRestored` and writes nothing; the file is retried (not a definitive failure). - quarantine (behavior change): a restoration never replaces an existing file (it fails with "destination already exists"; before, a file at the destination was overwritten). It is published with a hard link, else `RENAME_NOREPLACE`, and only else by a rename under a lock (a narrow window against another process, documented). The registry entry of a registered container is marked restored before the publication and put back if it fails; an entry that cannot be put back raises the console error `quarantine-restore-unmark-failed` (`quarantine.ErrRestoreRollbackFailed`). The registry takes its lock with the context of each call, so that a restoration (reads and writes bounded to 30 s) no longer waits behind a write that is stuck; a call that never returns (a hung disk or file system) still holds the lock until it does. A marking cut by its deadline is put back; a panic of the hook is logged. A restoration is refused toward the quarantine folder, the work directory, the staging area, the temporary names, a NUL and a path with `..`. New on `*QuarantineHandler`: `SetWorkDir` and `SetUnregisteredRestoreHook` (set by the connector as soon as its connector is made; the hook runs in a goroutine of its own; `quarantine.Config` is unchanged). - plugins: `GenerateReport` (the `HCContext` method and the plugin hook) now takes the reports as a sequence (`iter.Seq2[datamodel.Report, error]`, read once) and returns a `plugins.GeneratedReport{Content io.ReadCloser, Extension string}`: the extension comes from the generator, so without the `report` plugin the session report is a valid `.json` file instead of JSON named `.pdf`. Third-party report plugins must adapt to the new signature. The pipeline reports the end of every accepted file (`scanner.Config.OnFileDone`, `scanner.FileOutcome`, `Monitor.FileDone`): a definitive outcome is remembered until the file changes (the rescan compares its metadata, no content is read); a failure that may go away is retried after `2 × period`, doubling at each failure up to `64 × period` (one hour at most, ±20 % jitter) and given up at the 8th failure, except failures of a resource (timeout or full disk of an action, extractor down) which are never given up; a file modified while it was being analyzed waits for stability again, with or without a rescan. Plugins: every file or top-level archive for which `OnStartScanFile` was called now gets exactly one `OnFileScanned`, with an `Error` when its processing was abandoned (extractor down in the middle of an archive, archive lost by the handler, shutdown, file changed). The `session` plugin used to keep such a file "in progress" and its session open until shutdown. Anchor allow rules on the archive prefix (`^/in/...`): an unanchored rule also matches a member name chosen by the archive. A forbidden path is now applied even when the file cannot be examined. Reports keep their keys
- stability: the file the connector acts on is the one whose stability was observed and which was analyzed. The monitor identifies a file by device, inode, size, modification time and change time (`scanner.FileIdentity`; size and modification time elsewhere than Linux) and hands it to the pipeline with that identity. Public API change: `handler.OnNewFileFunc` is now `func(file string, id scanner.FileIdentity) (accepted bool, err error)` and `Connector.SubmitFile(ctx, input, want)` is new (`ScanFile` is kept). The file is opened once (never blocking on a FIFO, never following a link unless `follow_symlinks`), and its hash, its analysis (the connector looks the SHA256 up, submits the content read from the descriptor and waits for the result itself, so that the client makes no temporary copy; the SHA256 the service reports must match, for extracted members too), the plugins (`location` is a `/proc/<pid>/fd/<N>` path on Linux) and the extraction of archives (a link to the descriptor, in a folder of its own beside the output folder) read that descriptor. On Linux the connector refuses to start when `/proc/<pid>/fd` cannot be used; elsewhere it logs, at start, that the deposit path is used. After the last read the descriptor and the name are checked again, the descriptor is closed, and only then comes the action: a file substituted by `rename`, rewritten in place with its time restored, whose folder was swapped, or whose upload resumed is left untouched. The pre-scan and a folder created or moved into a monitored path go through the stability delay, walked by one queue; with `follow_symlinks: true` a link to a folder is never walked, by the monitor or by `scan`. A change made during the analysis is still only picked up at the next rescan (never with `monitoring.period: 0`)

A user folder mounted through a symbolic link under a monitored path is now refused: monitor its target, or mount the folder without a link (bind mount). A restoration outside the monitored paths checks its whole path from the filesystem root: a link is accepted only when it belongs to root in a directory of root that is not writable by the group or by others (at most 8 links, no exception for the sticky bit), and no folder is created there. The default base is the system temporary directory (`TMPDIR` honored): a site that monitors `/tmp` must set `work_dir` elsewhere. - actions on the verified file: the actions no longer receive a path but a `Source` (deposit path, monitored root, verified identity, and on Linux the descriptor opened without following any link). Any error puts the files back and leaves the previous registry and password in service
- quarantine: the quarantine directory is checked at every application of the configuration. It is refused, with the `chown` and `chmod` commands that fix it, when it belongs to another account than the connector or root or is writable by its group or by others; and when it is, is under, or contains a monitored path, `move.destination` or the work directory. A missing directory is created with mode `0700`. A site whose quarantine directory is group-writable or placed under a monitored path will not start after the update: run `chown <connector account> <dir> ; chmod 700 <dir>` or move the quarantine directory
- plugins: a relative `exports` directory of the `session` plugin is now refused (an output directory must be absolute so the connector can check where it is)
- plugins: the files loaded into the process (plugin `.so`, plugins file) are checked before they are opened: no link that is not a system link in their path, owned by root or the connector account, not writable by others (a group-writable one only warns, a refusal when the connector runs as root). A plugin cannot raise or clear the events of the core (`host-*`, `gmalware*`)
- plugins: a plugin may implement `Validator`: `Validate` runs for every plugin before a configuration is applied (with the previous one still running) in a scratch directory removed afterwards. `HCContext` gains `DeclareExecutable` (safety checks on a binary: owner, permissions, location), `DeclareOutputDir`, `NotifyError` and `NotifyResolution`. The connector refuses an output directory under a monitored path or the quarantine directory, and an executable under a monitored path, `move.destination` or an output directory. The plugins of the repository validate their configuration; `Close` of each is safe to call twice
- configuration file: a file that cannot be read or parsed, holds a mistyped value or a key the connector does not declare now stops the connector with an error naming the file and the key (never a value), instead of starting with defaults or ignoring the key. An absent file is still accepted, except when it is given with `--config`. Values are typed strictly like the console JSON (`workers: "4"`, `true` or `2.5` for a number are refused: quote strings, do not quote numbers) and a duration needs a unit (`5` is refused, `5m` is accepted; `0` stays valid). Upgrade notes: a leftover key such as the `cache:` section of the former `rsc/config.yml` must be removed or the connector will not start; and `follow_symlinks: true`, which had no effect from the file until now (the SDK key lacked its `mapstructure` tag), now takes effect: links are followed and the symbolic link checks are off. Remove the key to keep the previous behaviour
- configuration: connector-integration SDK v0.10.0 declares the new keys (`monitoring.*`, `move.mode`, `move.min_throughput`, `work_dir`, `unanalyzable_policy.*`, `quarantine.format`), and the connector applies all of them

### Fixed

- filetype_filter plugin: `forbidden_types` and `skipped_types` were never applied to a file deposited in the watched folders on Linux (the type was read from the descriptor link, which libmagic reports as a symbolic link): the whole file is now typed by libmagic through the descriptor the connector holds, so the type is the one `file` gives (a large MSI, Office file, APK or PIE executable included; a typing takes milliseconds on the files measured, with a pool of up to 8 handles and a limit of 5 s per call, the wait for a handle included, after which the file is refused when types are forbidden). The lists match on the type without its parameters and whatever the case (libmagic answers `application/SIMH-tape-data`, `application/grib;edition=1`); **Behavior change:** the configuration is now refused at start (and by the console) when `forbidden_types` or `skipped_types` holds an entry that could never match (an empty entry, a space, a parameter such as `application/grib;edition=1`, something that is not `type/subtype`) or when `skipped_types` holds `application/octet-stream`: remove the entry, or write the type without parameters. Behavior change: a file larger than 7 MiB (`bytes_max` of libmagic) is no longer waived by `skipped_types`, it is analyzed, since its type is found from a part of it; `forbidden_types` still applies to it. A file that cannot be typed (made unreadable after it was deposited, a libmagic failure) is refused with an error when `forbidden_types` is not empty (it stays in its folder) and left to the analysis with a warning otherwise. A content libmagic does not recognize, or types `application/octet-stream`, is of that generic type, which `forbidden_types` can refuse and `skipped_types` never waives (the configuration is refused when `skipped_types` lists it); when libmagic cannot be opened or recognizes nothing the configuration is refused if `forbidden_types` is set and a warning is logged otherwise. An empty file no longer stops the plugin
- extract plugin: a 7z with encrypted headers (`7z a -mhe=on -p...`) and a known password (`infected` by default) is extracted: it failed with a raw `exit status 2` because 7-Zip words the refusal of the first attempt, made without a password, on two lines when it extracts, and only the one-line wording of the listing was recognized
- extract plugin: 7-Zip is now run on a link named by the plugin (the name of the archive with every character outside letters, digits and ` ._+@=,~()-` replaced by `_`, cut to 100 bytes, keeping up to two extensions), so that the path it prints in an error is always one the plugin can neutralize. A header-less `.gz`, `.bz2`, `.xz` or `.zst` (7-Zip names its member after the archive) therefore has a member named after that staged name; a staging failure (the work directory cannot be used) raises the extractor-unavailable alert
- extract plugin (behavior change): because 7-Zip is run on a link, it no longer sees the files next to the archive: the volumes of a multi-volume archive (`x.7z.001`, `x.7z.002`) are each handled on their own, as an archive that cannot be read whole
- extract plugin: 7-Zip repeats names of the archive raw in some errors (a member it cannot create, the target of a link), so a name with a newline could write a line of 7-Zip's errors, such as "Wrong password", and make a crafted archive, even a tar, pass for an encrypted one. After a line that repeats a name nothing is believed: after a member that cannot be created (or a label that is not known to carry no name) its errno decides, and after a refused link every other error line counts as damage. A member that goes through a file, is a directory, loops or has a name too long (ENOTDIR, EISDIR, ELOOP, ENAMETOOLONG), and a link toward a target that is not in the archive, is a damaged archive (an anomaly, encryption possible, no retry); any other errno of a member that cannot be created (permission, space, quota, read-only, I/O, descriptors) is the host's and is retried. A folder over a file the archive made before (EEXIST) and a link toward a directory (EPERM) are damage too. A line that is only the label of a refused link, or has an empty name, is not a refused link. Accepted limits: a hard link toward a member left out of the extraction for its size gives the same error as a missing target, so the archive is an anomaly; ENOTDIR and ELOOP caused by a process of the host that changes the output folder fail the archive closed instead of retrying it; a real refusal of the host in the same run as a real refused link is a definitive anomaly instead of a retry
- monitoring: a directory that cannot be read during a periodic rescan no longer stops the walk of the other directories
